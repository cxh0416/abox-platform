## 1. VID：保留 V5

保留巡防车 Config V5：结构 400 字节、版本 5、TLS 字段偏移 396/397、CRC、恢复槽及既有读写流程不变。取消 V6、清除旧配置、32 字符缓存扩容、迁移与多版本分支；不增加容量协商或 Manifest 字段。公共接收端仍允许合法的 32 字符标识。32 字符设备配置尚未覆盖，作为能力差异记录；真正发号需要时再核查整条链路，不默认升级所有内部存储。

## 2. 已完成与继续保留的摘要行为

公共 [SHA-256](../../components/mqtt/include/abox_sha256.h) 来自送餐车已有实现，不依赖新密码库；[流式规范化/请求摘要](../../components/mqtt/include/abox_mqtt_digest.h) 不分配规范化大缓冲区。对象按 UTF-16 键序排列，普通数组保持顺序，字符串不做 Unicode 归一化；摘要只包含 `command`、归一化 `params` 和存在时的 `expiresAt`，不包含 `requestId`、外层 timestamp。业务集合归一化由 Profile 承担，不能排序普通数组。

公共 C 序列化与 Python 规范参考、冻结固定向量逐字节及逐摘要对照；验证空串、abc、百万 a 的 SHA-256，以及实际旧 FNV 碰撞对不同 SHA-256。辅助 cJSON wire parser 显式拒绝重复 key、整数越界、分数/指数/-0、无效 UTF-8、不可表示的 NUL，并限制解析深度；这些是该适配器的能力边界，**没有作为公共协议的新字段/长度/深度规则发布，也没有替换三个产品的整个报文接收端**。

本轮三个产品需要内容比较的业务请求摘要已接入公共平台：送餐车格口、电源、显示、sync_state；巡防车运动、电源；清扫车电源。送餐车只负责格口数值集合排序和显示HEX大写化，公共平台负责请求对象、标量编码和SHA生命周期，不再用384字节完整请求缓冲区计算格口摘要。巡防车将64字节运动元组换成SHA32；四条电源记录保持原布局，按已保存的完整业务字段重建原摘要后比较，没有为每条记录再增加32字节常驻缓存。清扫车也按同样方式重建null-params电源请求摘要，保护窗口和首次状态快照保持。

已有转角解析结果本来就是毫度整数。公共 `WriteMilli` 将其编码为确定的JCS度值（例如 -200→-0.2、1000→1、0→0），没有把线上单位改成毫度，也没有开放通用浮点接收。全部60001个 -30°～30°毫度值与Node/ECMAScript JSON.stringify逐字节一致，运动摘要另有固定SHA与真实FNV碰撞回归。这足以继续收敛摘要实现；**公共“所有数字为整数”与已有转角Profile的文档矛盾仍然存在，正式条文未擅自修改**。产品解析器已有的扩展字段处理和业务归一化保持，辅助通用cJSON整数解析器没有代替产品接收端。

## 4. 跨重启防重：RAM 门槛暂停接入

既有巡防车/清扫车四条 RAM power_on记录在初始化清空，仍不能保护跨重启的历史重投。没有通过修正文档把该缺陷说成合规，也没有把“仅保护最后一个请求”作为替代。

三 App重新构建后，使用 ARM nm与真实 ARM sizeof评估。复现工具：[assess_power_replay_ram.py](../../tools/assess_power_replay_ram.py)，传入两产品的验证 ELF。固定邮箱 `0x2000BC40`、_sstack与既有堆/栈/4 KiB guard全部保留。

| 项目 | 巡防车 | 清扫车 |
|---|---:|---:|
| _ebss到固定邮箱剩余（此次SHA接入后） | 44 B | 20 B |
| 既有 reserved_end到栈保护边界剩余 | 8 B | 8 B |
| 公共 ABoxEc800Ufs上下文（ARM sizeof） | 120 B | 120 B |
| 候选完整响应记录（65字节ID、SHA32、expiresAt、288字节响应、状态/长度） | 408 B | 408 B |
| 四记录快照（含头/CRC，ARM sizeof） | 1656 B | 1656 B |
| 当前快照+候选/回读复用快照+UFS（未计调度/路径/摘要校验状态） | 3432 B | 3432 B |

上述为简单双槽方案的**布局估算**，不是已接入的事务实现，更不是所有低内存算法均不可能的证明。即使抵扣巡防车已有 384 B缓存仍需 3048 B；清扫车即使抵扣约半 KiB既有缓存也仍远超剩余空间。当前通用 UFS接口还要求传输缓冲区在异步操作期间持续有效；复用 MQTT发送缓冲区会影响并发心跳/响应，不能假定安全。当前静态 RAM gate为 STOP，未缩小栈、Boot邮箱、已有恢复工作区或内存保护来强行通过，也未将长期缓存挪进动态堆掩盖并发占用。

因此本轮**停止持久化接入**，未新增 UFS文件、事务状态机、初始化分支或产品执行适配；4条RAM记录行为不变。PREPARED/FINAL、整个 expiresAt+10分钟窗口、满容量拒绝、双损坏不视为空表、下电取消未执行上电等要求仍为下一方案的验收条件。UFS提交延时、写入频率/寿命、准备/执行/响应保存各阶段实机断电测试尚未开展，不能称为通过。

### 4.1 实际危害重评：现场旧版与当前源码必须分开

2026-10-13只读Ops查询确认：`PATROL-05D3FF343733574E43043550`运行0.2.45，最近心跳timestamp=0；`SWP-05DCFF363931524743133129`运行1.3.23，最近心跳Epoch正常。平台服务运行0.4.181。没有发送get_info、上/下电、重启或OTA；设备版本来自已存心跳，不能把最新源码当作现场固件。

| 对象 | 已核实保护及实际后果 |
|---|---|
| 现场巡防0.2.45 | 对应源码（2edf4bc040d42461b4fd6aec2cf11c7c8b9dbc85，VERSION=0.2.45）在ChassisCloud_Parse的power分支只检查params:null，不读timestamp/expiresAt；RemoteService电源分支直接写输出，没有四条power缓存。若公共上电入口仍被允许、旧报文再次送达且输出可用，旧power_on可以在已下电后重新打开OUT1，**不限5秒，也不只限跨重启**。若OUT1连接整车/底盘供电控制，相关负载可能重新得电；不能据此声称必然行走或已发生现场事故 |
| 现场清扫1.3.23及当前两产品源码 | 上电原始有效期最多5秒，首次新请求必须通过可信UTC有效期校验；普通MQTT重连保留电源缓存。两产品main先绑定标准板电源配置，模组启动最短off_hold6000+rail_stable2000+key_hold3000=11秒，连接等待IsOnDone，时间信任从启动重新建立。正常授时、原报文时间正常的标准MCU重启中，旧请求在能执行前已经过期，不会因缺持久化而重新上电 |

这里确认的是对应旧版源码的接收缺陷，未证实现场已发生旧消息重投或意外上电。公共契约禁止Retained Request并要求Clean Session=true；不能据RAM缓存丢失推断Broker一定跨重启排队。危险仍以旧合法请求实际再次送达、业务入口获准且输出可用为前提。

当前源码的确定缺口是**不能恢复首次处理结果**：原来已经接受/执行的请求，重启后可能得到4003或4005，丢失历史响应，平台不能从重投响应判断它之前是否曾经执行。这与“旧消息重新打开电源”是两种不同问题。发送端业务超时测试确认两产品上电只派发一次，TTL不会因操作超时被刷新；MQTT自身QoS1重投仍可能发生，传输ACK不代表设备执行完成。

新增真实产品handler/power模块主机测试验证：同次运行下电后重投返回原状态但不驱动；模拟标准启动经过11秒，时间不可信返回4003、可信后返回4005且输出保持关；人为构造“2秒内只清缓存、仍有可信时间”的非标准路径才再次上电。这是条件验证，**不是实机重启或危险报文重投**。UTC大幅错误/回拨、未来保留模组的快速热启动或在线重置缓存，会改变结论，应重新核查；没有证据认定这些已在现场发生。

最小建议：先处理现场巡防旧版的有效期/去重缺失。当前源码已有修复，下一步是解决旧版→修复版的可靠启动/升级验证；其0.2.54曾回滚，不能直接假定新包可安全上线。在可靠修复版上线前，评估用既有准入手段暂停这台旧版公共远程上电，保留下电/查询；本轮没有修改线上门禁。**暂不增加启动会话**：它需要旧设备固件支持，无法只修改新源码就保护仍运行的0.2.45；对已有正常启动保护的设备，是否值得为历史响应一致性增加存储或会话，需按业务要求另作决定。

### 4.2 启动会话备选评估（未选定、未实施）

只有后续确认需要额外跨启动授权约束时，才评估为两产品power_on引入Profile级启动会话：每次启动取得新鲜且绑定设备身份的会话标识；平台确认当前会话后才生成上电请求，旧会话不能上电。高频运动仍使用已有sessionId/seq/lease；查询、心跳、Report和下电不逐条落盘。会话可由平台生成并经受控通道获取，不默认要求STM32F105硬件RNG或升级模组固件。会话约束本身不会保存首次响应，不能用它宣称恢复了历史结果。

这是未来协调的 Profile/平台契约变化，不是本轮可直接实现的固件修复：必须确定具体字段、获取/失联规则、重新连接是否续用、重投首次响应规则及版本。不能用 requestId私有前缀、设备 timestamp推断启动或单纯清平台待发队列宣称等价跨重启安全；Broker中已排队的旧上电仍可能到达。不增加旧新双套配置解析或隐式回退。确认后再安排两产品与平台一次受控升级；送餐车是否需要纳入另行评估，不默认扩大范围。

若之后仍选择双槽：首先论证流式磁盘索引/响应读取能否节省 RAM且不占用 MQTT缓存，再提供可信的首次初始化依据（明确区分首次无文件、文件丢失、I/O失败与双槽损坏），然后实测5秒请求有效期内的提交+回读+执行前时间复核。未满足之前不启用上电持久化路径。
