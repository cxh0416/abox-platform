# MQTT V4 收敛处置记录（内部）

日期：2026-10-13。这是当前代码、容量评估及待确认条文的记录，不是公共协议入口、发布批准或实机验收。范围仅公共平台、送餐车、巡防车、清扫车及相关平台服务；不涉及其他产品迁移、冻结 Boot、OTA 或生产数据库操作。

## 1. VID：保留 V5

公共 V4 第 2.3 节的 `deviceId` 1～32 ASCII 字符定义，已存在于初次冻结提交 `dc22f4b`（2026-09-16），是正式公共契约；未找到“业务必须发满 32 位”的依据。上限规定不要求每台设备的持久化格式立即扩容。当前发号、入网凭据、审批、改号、试运行与产品配置采用最多 31 字符；`V050006` 长 7，完全覆盖实际规划。

保留巡防车 Config V5：结构 400 字节、版本 5、TLS 字段偏移 396/397、CRC、恢复槽及既有读写流程不变。取消 V6、清除旧配置、32 字符缓存扩容、迁移与多版本分支；不增加容量协商或 Manifest 字段。公共接收端仍允许合法的 32 字符标识。32 字符设备配置尚未覆盖，作为能力差异记录；真正发号需要时再核查整条链路，不默认升级所有内部存储。

| 入口 | 当前规则与此次处理 |
|---|---|
| 发号/入网 | 保留 `[A-Za-z0-9_-]{1,31}`；不强制 `V` 加六位数字。不再把首尾空白或非字符串 VID 转换成另一个有效标识 |
| 审批 | 保存凭据、修改审批状态及调用 Broker 前复核完整 canonical VID；非法或超容量失败。独立 UID、凭据代次、全局 VID 归属与现有事务不变 |
| 平台改号 | 既有 31 字符校验、跨产品占用检查和审批凭据绑定保留；增加完整 31 字符及拒绝无副作用回归 |
| 巡防车运维解析 | 移除允许 `.` 的字符集例外；空值、非法字符、32/33 字符失败 |
| V5 保存/试运行 | 保存前校验完整 VID；`SetMqtt` 不再截断超长 VID。持久候选与首次入网在 staging 之前校验，不启动部分切换 |
| MQTT 身份应用 | VID 校验先于 ClientId、Topic、时间同步订阅更新。31 字符成功路径仍使用完整 VID |

代码：巡防车 `patrol_config.c`、`cloud_protocol.c`、`mqtt_trial_manager.c`、`cloud_service.c`；服务端 `device_ota/services/abox_enrollment.py` 与既有 `vid_migration.py`。非法输入测试核对 RAM 配置、Flash 快照、秘密快照、staging 次数和身份更新次数均未改变；实际 MQTT 身份函数的早拒绝顺序另经源码核对，未把 host mock 视为模组验证。

## 2. 已完成与继续保留的摘要行为

公共 [SHA-256](../../components/mqtt/include/abox_sha256.h) 来自送餐车已有实现，不依赖新密码库；[流式规范化/请求摘要](../../components/mqtt/include/abox_mqtt_digest.h) 不分配规范化大缓冲区。对象按 UTF-16 键序排列，普通数组保持顺序，字符串不做 Unicode 归一化；摘要只包含 `command`、归一化 `params` 和存在时的 `expiresAt`，不包含 `requestId`、外层 timestamp。业务集合归一化由 Profile 承担，不能排序普通数组。

公共 C 序列化与 Python 规范参考、冻结固定向量逐字节及逐摘要对照；验证空串、abc、百万 a 的 SHA-256，以及实际旧 FNV 碰撞对不同 SHA-256。辅助 cJSON wire parser 显式拒绝重复 key、整数越界、分数/指数/-0、无效 UTF-8、不可表示的 NUL，并限制解析深度；这些是该适配器的能力边界，**没有作为公共协议的新字段/长度/深度规则发布，也没有替换三个产品的整个报文接收端**。

送餐车删除私有 SHA 源文件，保留头文件兼容入口；电源及 `sync_state` 改用公共流式摘要，显示大写 HEX 与格口集合的既有归一化仍由产品实现，计算结果保持一致。巡防车仍保留此前修复的精确运动元组比较，不恢复 FNV，也未将尚不支持小数的公共整数序列化强接到转角路径。**公共摘要能力已具备，三个产品所有 Profile 的摘要接入尚未全部完成**；转角的正式条文确认前不能宣布巡防车完全符合冻结摘要要求。

## 4. 跨重启防重：RAM 门槛暂停接入

既有巡防车/清扫车四条 RAM power_on记录在初始化清空，仍不能保护跨重启的历史重投。没有通过修正文档把该缺陷说成合规，也没有把“仅保护最后一个请求”作为替代。

三 App重新构建后，使用 ARM nm与真实 ARM sizeof评估。复现工具：[assess_power_replay_ram.py](../../tools/assess_power_replay_ram.py)，传入两产品的验证 ELF。固定邮箱 `0x2000BC40`、_sstack与既有堆/栈/4 KiB guard全部保留。

| 项目 | 巡防车 | 清扫车 |
|---|---:|---:|
| _ebss到固定邮箱剩余 | 12 B | 20 B |
| 既有 reserved_end到栈保护边界剩余 | 8 B | 8 B |
| 公共 ABoxEc800Ufs上下文（ARM sizeof） | 120 B | 120 B |
| 候选完整响应记录（65字节ID、SHA32、expiresAt、288字节响应、状态/长度） | 408 B | 408 B |
| 四记录快照（含头/CRC，ARM sizeof） | 1656 B | 1656 B |
| 当前快照+候选/回读复用快照+UFS（未计调度/路径/摘要校验状态） | 3432 B | 3432 B |

上述为简单双槽方案的**布局估算**，不是已接入的事务实现，更不是所有低内存算法均不可能的证明。即使抵扣巡防车已有 384 B缓存仍需 3048 B；清扫车即使抵扣约半 KiB既有缓存也仍远超剩余空间。当前通用 UFS接口还要求传输缓冲区在异步操作期间持续有效；复用 MQTT发送缓冲区会影响并发心跳/响应，不能假定安全。当前静态 RAM gate为 STOP，未缩小栈、Boot邮箱、已有恢复工作区或内存保护来强行通过，也未将长期缓存挪进动态堆掩盖并发占用。

因此本轮**停止持久化接入**，未新增 UFS文件、事务状态机、初始化分支或产品执行适配；4条RAM记录行为不变。PREPARED/FINAL、整个 expiresAt+10分钟窗口、满容量拒绝、双损坏不视为空表、下电取消未执行上电等要求仍为下一方案的验收条件。UFS提交延时、写入频率/寿命、准备/执行/响应保存各阶段实机断电测试尚未开展，不能称为通过。

### 启动会话替代方案评估（未实施）

优先评估为巡防车与清扫车的 power_on引入 Profile级启动会话约束：每次启动取得新鲜且绑定设备身份的会话标识；平台仅在确认当前会话后生成上电请求，旧会话请求不能上电。高频运动继续使用已有 sessionId/seq/lease；查询、心跳、Report和下电不逐条落盘。会话标识可由平台安全生成并通过受控通道获取，不默认要求 STM32F105增加硬件 RNG或升级模组固件。

这是未来协调的 Profile/平台契约变化，不是本轮可直接实现的固件修复：必须确定具体字段、获取/失联规则、重新连接是否续用、重投首次响应规则及版本。不能用 requestId私有前缀、设备 timestamp推断启动或单纯清平台待发队列宣称等价跨重启安全；Broker中已排队的旧上电仍可能到达。不增加旧新双套配置解析或隐式回退。确认后再安排两产品与平台一次受控升级；送餐车是否需要纳入另行评估，不默认扩大范围。

若之后仍选择双槽：首先论证流式磁盘索引/响应读取能否节省 RAM且不占用 MQTT缓存，再提供可信的首次初始化依据（明确区分首次无文件、文件丢失、I/O失败与双槽损坏），然后实测5秒请求有效期内的提交+回读+执行前时间复核。未满足之前不启用上电持久化路径。
